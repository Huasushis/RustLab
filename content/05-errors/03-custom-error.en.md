title: Custom Error Types
---
Using `String` as the error type is convenient, but callers can't react to different **kinds** of errors except by comparing strings. The principled way is an enum listing every way things can fail:

```rust
#[derive(Debug)]
enum ConfigError {
    Missing(String),            // a config key is missing
    BadNumber(ParseIntError),   // wraps the underlying error
}
```

Now callers can `match` on it, and when you add a new kind of error later, the compiler reminds every place that handles it. It's the equivalent of an exception class hierarchy in C++ / Python, built with an enum instead of inheritance.

## Making it a "proper" error: implement Display

`Debug` (`{:?}`) is for developers and can be derived; `Display` (`{}`) is for users and has to be written by hand:

```rust
use std::fmt;

impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            ConfigError::Missing(key) => write!(f, "missing config key {key}"),
            ConfigError::BadNumber(e) => write!(f, "malformed number: {e}"),
        }
    }
}

impl std::error::Error for ConfigError {}   // marks it as an error type; usually no methods needed
```

`write!` works like `println!`, but writes into its first argument `f`. Any type that implements `Display` automatically gets a `.to_string()` method.

## Let ? convert errors automatically with From

In the previous level we converted error types by hand with `map_err`. In fact, before returning an error, `?` automatically calls `From::from` on it. So all you need is to tell the compiler how a `ParseIntError` becomes a `ConfigError`:

```rust
impl From<ParseIntError> for ConfigError {
    fn from(e: ParseIntError) -> Self {
        ConfigError::BadNumber(e)
    }
}

fn parse_port(s: &str) -> Result<u16, ConfigError> {
    let port = s.parse::<u16>()?;     // the ParseIntError is wrapped into ConfigError::BadNumber automatically
    Ok(port)
}
```

> In real projects this boilerplate is usually generated by the `thiserror` (for libraries) or `anyhow` (for applications) crates. Chapter 11 shows them — they do exactly what you write by hand in this level.

:::solution
use std::fmt;
use std::num::ParseIntError;

#[derive(Debug, PartialEq)]
enum ParseError {
    Empty,
    BadNumber(ParseIntError),
    NotPositive,
}

impl fmt::Display for ParseError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            ParseError::Empty => write!(f, "empty input"),
            ParseError::BadNumber(_) => write!(f, "not a number"),
            ParseError::NotPositive => write!(f, "must be positive"),
        }
    }
}

impl std::error::Error for ParseError {}

impl From<ParseIntError> for ParseError {
    fn from(e: ParseIntError) -> Self {
        ParseError::BadNumber(e)
    }
}

fn parse_positive(s: &str) -> Result<i64, ParseError> {
    let s = s.trim();
    if s.is_empty() {
        return Err(ParseError::Empty);
    }
    let n = s.parse::<i64>()?;
    if n <= 0 {
        return Err(ParseError::NotPositive);
    }
    Ok(n)
}

fn main() {
    for input in ["42", "  7 ", "", "abc", "-3", "0"] {
        match parse_positive(input) {
            Ok(n) => println!("{input:?} -> {n}"),
            Err(e) => println!("{input:?} -> error: {e}"),
        }
    }
}
